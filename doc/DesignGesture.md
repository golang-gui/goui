# GUI 手势竞争设计

> 状态：首版已接入 GUI 内核和内置控制器；跨平台原生接管与组合窗口场景仍需桌面验收。
> 宿主公共状态保留 `rootBase` 名称，不引入新的公共 Root 对象。
> 关联：[GUI 输入分发](../gui/event.go)、
> [窗口 Chrome](DesignGUIWindowChrome.md)、[平台窗口交互接口](../platform/common/window.go)。

## 1. 目标与边界

一次按下可能最终成为点击、双击或拖动。框架应允许多个控制器先观察同一段输入，
再确定交互归属，而不是由最早收到 PointerDown 的控制器直接占有后续事件。

主要场景：

- ScrollView 中的 Button：按下显示反馈，移动超过阈值后滚动接管，抬起不能再点击按钮。
- 同一控件同时支持点击和拖动：未移动时点击，超过阈值后拖动。
- 第二次点击原本可能构成双击，但随后移动：取消双击候选，转为拖动。
- HeaderBar：单击无动作，双击最大化/恢复，任一次按下后移动均可拖动窗口。

首版仅处理单指针、同一鼠标按钮的一段输入，最终只有一个获胜者。
不实现多指手势、同时识别、任意优先级、识别器依赖图，也不支持获胜后将滚动交给父容器。
不同按钮的输入不能加入同一个竞争序列；另一按钮的 Down 中断旧序列，随后建立新序列。

## 2. 分层与当前实现的差异

平台只提供原生输入和窗口操作机制，不识别 Widget 点击或决定滚动策略。
真实与模拟输入均经由既有 Window.DispatchEvent 进入 GUI 输入路径。

| 部分 | 职责 |
| --- | --- |
| EventDispatcher | 命中、传播、候选收集、竞争期间及获胜之后的事件路由 |
| 内部手势协调器 | 保存本段输入的参与者，处理申请、裁决、拒绝和取消 |
| EventController | 识别自己的条件、申请或放弃竞争，将获胜结果转为控件信号 |
| Widget | 根据按压、点击、拖动等信号更新状态和执行动作 |

协调器首版作为 Dispatcher 的内部实现，不先公开独立的 Arena 对象。
普通事件控制器不应被迫参与竞争；自定义控制器需要有明确、可选择的参与方式。

Click、Drag、文本选择、DragSource 与非原生 Chrome 已通过可选参与协议接入。
DragEventController 默认按下即申请，`SetThreshold` 可改为阈值拖动；ScrollBar
继续采用默认立即拖动。Dispatcher 的 `captureTarget` 只反映已接受者，
不再扫描 `PointerCaptureController`。

StopPropagation 与申请手势所有权是不同操作：前者控制当前事件的传播，后者决定
后续整段交互的归属。不能用停止传播代替申请获胜，也不能让识别器因申请而立即执行动作。

## 3. 生命周期与裁决

参与者状态按以下方向转换：

```text
候选 ──申请──> 待裁决 ──被选中──> 获胜 ──完成──> 结束
  │                 └─未选中──> 拒绝
  ├─主动放弃──────────────────> 拒绝
  └─交互失效──────────────────> 取消
获胜 ──交互失效───────────────> 取消
```

申请获胜不等于已经获胜。协调器在当前事件的候选处理阶段结束后统一裁决，
不能因父控件在 Capture 阶段先收到事件就立即宣布它获胜。

首版裁决规则：

1. 只有一个有效申请者时，该申请者获胜。
2. 同一事件多个申请者时，优先初始命中路径中更深的控件。
3. 同一控件多个申请者时，按控制器注册顺序决定。
4. 没有申请者时继续等待；全部拒绝时结束竞争。
5. 拒绝或取消的参与者不能重新加入当前交互；获胜后不重新竞争。

裁决后先使其他候选失效并撤销按压反馈，再通知获胜者执行动作。
取消回调可能卸载或销毁控件，故通知获胜者前必须重新检查其有效性。
同一个控制器不能因为经历多个传播阶段而重复加入同一序列。

## 4. 点击、双击与拖动

### 4.1 识别时机

| 识别器 | 候选阶段 | 申请获胜的时机 |
| --- | --- | --- |
| 点击 | 按压反馈，等待有效抬起 | 有效抬起 |
| 双击识别 | 保存前次点击记录，本次按下仅是候选 | 第二次有效抬起 |
| 拖动 | 保存本次起点，等待移动 | 位移超过拖动阈值 |

双击是点击识别器跨两段输入保存的序列信息，不要求第一段竞争持续到第二次点击。
不建议将普通点击和双击拆成两个独立争抢的识别器，否则同一抬起又会产生不必要的裁决。
ClickEventController 保留 `ConnectClicked`，并提供 `ConnectClick` 上报完成点击的
次数 1 或 2；需要区分单双击的使用方只连接后者，避免重复执行动作。

### 4.2 双击候选如何转为其他操作

- 第二次按下符合时间和位置条件时，只标记为双击候选，不立即执行双击动作。
- 第二次移动超过阈值时，点击候选失去资格，拖动申请获胜；起点是第二次按下的位置。
- 第二次有效抬起且仍满足双击条件时，双击成立。
- 第二次不再满足双击条件，但仍符合普通点击条件时，按普通点击处理。
- 超时本身不立即产生点击，仍需等待有效抬起；失焦、卸载等取消不能强制降级为点击。
- 已进入拖动后，即使指针返回起点也不重新成为点击。

这里的“降级”是未决识别结果的变化，不是撤销已经执行的动作，更不是向其他控件
重发一组伪造的 PointerDown/Move/Up。

### 4.3 第一次点击是否等待

首版选择第一次有效点击立即通知，不等待双击超时。
第二段交互最终成为拖动时，第一段点击已经完成，不回滚。
这意味着单击与随后双击不是互斥动作；需要互斥的控件将来应显式选择延迟策略，
不能让所有 Button 承担等待双击的延迟。

初始阈值沿用现有 Caption 的 500ms、4 DIP，并集中管理，避免各识别器复制常量。
精确的时间边界、距离计算及阈值配置接口在实现设计时统一锁定；本草案不增加平台设置 API。
首版双击结束后清空点击序列，下一次点击重新开始，不扩展三击或任意点击计数。

## 5. 路由、反馈与取消

竞争期间保存初始参与路径，允许原候选在指针移出控件后继续收到必要的移动和抬起。
这不等于宣布某个 Widget 获胜，也不应冻结独立的 hover 命中和光标更新。

获胜后，手势相关的后续输入定向交给获胜控制器；其它候选不能再次生成点击或拖动结果。
这是 GUI 的逻辑路由，不声明原生捕获能力，也不保证操作系统一定会交还鼠标抬起。

按压反馈属于可撤销的暂态，允许在候选期显示；业务点击、开始实际滚动和窗口状态切换
属于确定动作，必须等到相应识别结果获胜。拖动可在获胜后持续更新内容。

取消来源至少包括窗口失焦、模态接管、参与控件隐藏或卸载、控制器移除、控件/窗口销毁，
以及原生输入接管导致当前 GUI 路由失效。移出某个 Widget 本身不等同于取消整段竞争。

清理必须同时处理协调器记录、控制器状态和捕获归属，不能只清空 captureTarget。
完成和取消互斥；一次生命周期最多结束一次。回调内 Reset、卸载、销毁或重入派发后，
旧序列不得继续发送过期通知。EventContext 和结果指针只在同步调用期间有效。

## 6. Caption 与原生窗口操作

HeaderBar 继续负责提供 ChromeRegionCaption，不自行改变窗口状态。
Chrome 在非原生命中路径上复用识别规则：单击无动作、双击抬起请求最大化/恢复、
任一次按下后超过阈值请求 BeginMove。Windows 原生 Caption 路径不重复加入 GUI 识别。

BeginMove 必须在当前原生按住移动事件的同步处理期间启动。协调器的裁决不能投递到
下一轮事件循环，否则原生输入上下文已经失效。原生接管后结束 GUI 手势路由，
不能等待一个可能已由窗口管理器消费的抬起，也不能重新把失败的拖动变为点击。

Chrome 的宿主控制器仍先接收 Down，但以深度 -1 加入同一竞争序列；
命中的 Widget 候选同时申请时优先获胜。HeaderBar 的 Client 判定继续排除子控件。

## 7. 已实现的参与协议与迁移

```go
type GestureController interface {
    EventController
    GestureAccepted(EventContext)
    GestureCanceled(GestureCancelReason)
}

func JoinGesture(EventContext) *GestureParticipation
func (*GestureParticipation) Claim()
func (*GestureParticipation) Reject()
```

`JoinGesture` 只能由当前收到 PointerDown 的控制器调用；同一控制器在同一序列重复加入
返回同一凭证。Claim 只提交申请，同一事件处理结束后同步裁决。Reject 可由 GUI 线程
上的 Reset/禁用调用，过期凭证不再产生效果。完成或取消后清理凭证。

共享的 `rootBase` 持有 Dispatcher、原生 DnD 服务和目标状态；Popover 的原生回调
由 surface 代次隔离，旧 surface 的源会话结果仍交给 Application 清理。
目标端 DnD 没有本地 Down，仍按原生 Offer 路径协商，不加入手势竞争。

本轮迁移了 Click、Drag、文本选择、DragSource、非原生 Chrome 和按压反馈；
Button 不再在候选按压时停止传播。原生 Begin 之前结束 GUI 序列；
Begin 失败后不重新触发 Click。ScrollView 的鼠标拖动滚动不在本轮范围。

旧 `PointerCaptureController` 分发扫描与 Chrome 独立处理分支已移除。
Chrome 测试用可控时钟经 Window.DispatchEvent 验证双击和第二次按下转拖动。

## 8. 验收场景

- Button 位于可拖动容器内：单击只点击；拖动时按钮撤销按压反馈，不能在抬起后点击。
- 第一次点击后，第二次有效抬起成为双击；第二次越过阈值则只产生该次拖动。
- 超时、距离超限、长按、抬起位置无效分别得到明确结果，不误发双击或强制点击。
- 同事件父子申请、同 Widget 多控制器申请、全部拒绝、重复申请均遵守裁决规则。
- 候选期移出控件仍能识别拖动；获胜后输入路由稳定，hover 不被错误冻结。
- 回调中取消、Reset、移除控制器、卸载、销毁和重入不会生成过期动作或遗留捕获。
- ScrollBar 等旧式立即拖动不因新机制出现额外启动延迟。
- Caption 单击不移动；第二次按下后拖动不先最大化；Windows 不产生重复状态请求。
- 原生移动接管、未返回抬起、移动请求失败均不留下 GUI 按压或竞争状态。

数学与状态机测试使用可控制时间，不依赖 sleep；路由测试经 Window.DispatchEvent，
再用三平台真机验证系统接管行为。实现完成后执行 go test ./... 和跨平台编译；
编译通过不代替原生输入验收。
